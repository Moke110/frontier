# ADR 0009：控制台成为 frontier 的唯一运行入口

- 日期：2026-10-30
- 状态：已接受；实现已合入（离线测试通过），真实验收见 `docs/acceptance/README.md`
- 替代：[ADR 0008](0008-listener-process.md)（监听进程 + 宿主定时任务）
- 修订：[ADR 0005](0005-agent-owned-execution.md) 中"不创建独立常驻程序"与"宿主定时任务"的约定；[ADR 0006](0006-deepseek-harness-as-a-host.md) 中 DSH 会话级定时的运行地位
- 相关：[ADR 0007](0007-reuse-configured-lark-cli.md)（复用已配置的 lark-cli）、[ADR 0003](0003-lark-as-only-storage.md)（飞书存储）

## 背景

ADR 0008 之后，frontier 有两个运行主体：用户手动启停的 `frontier-listener` 前台进程，以及宿主的两个定时任务（`frontier-daily` 08:00、`frontier-listener-check` 09:00）。用户提出的新要求把这两者合并成一个终端控制台：

1. 用户通过控制台获得运行信息；**关闭控制台即停止 frontier 服务**；
2. 定时推送、监听飞书输入、把飞书输入转化为指令交给执行 agent，都由控制台承担；
3. 安装流程从"agent 会话里完成一切"改为"agent 装好并启动控制台，用户在控制台里初始化"；
4. 知识库初始化改为控制台内逐条审阅，支持 `Under review` 保留态。

"24 小时在线"不再由监听进程与宿主巡检拼出来，而是**控制台在前台就代表在线**。宿主的定时能力（尤其是 DSH 的会话级定时）因此退出一线：它既不负责调度，也不负责在线证明。

## 决策

### 1. 控制台是唯一常驻入口与唯一调度者

- 新增常驻入口 `python -m hostrun.cli console`，用户可双击 `<code>/bin/frontier-console.cmd` 启动（窗口标题 `frontier-console`）。
- 控制台在进程内承担：每日定时推送、飞书事件消费（消息与卡片回调）、每 5 分钟反馈轮询、每 10 分钟知识库拉取、agent 运行的启动与收尾、终端交互、单实例锁、心跳与滚动日志。
- `listener` 子命令与其启停脚本退役为兼容别名或直接移除；`listener-check` intent 与 `frontier-listener-check` 任务退役；两个宿主定时任务不再创建。
- 关闭窗口即停止服务；机器重启后服务不会自行恢复，必须用户重新打开控制台。不进 Windows 服务、不登录自启、不写注册表或系统定时任务。

### 2. 目录模型重划

用户原则：**资料目录只放原文与推送件；代码、环境、配置、登记文件全在代码目录。**

- 顶层参数：`--code <代码目录>`（默认仓库根）+ `--archive <资料目录>`（默认 `<root>/frontier-archive`）。原 `--home` 退役。
- 代码目录承载：代码、私有 Python 环境、配置、运行状态、队列、提议、日志、执行端租约、控制台状态、安装记录、资料登记、私有 lark-cli。
- 资料目录只允许出现两类文件：`originals/`（原文 PDF）与 `pushes/`（推送件），且不再含任何台账。
- 资料登记是代码目录里按业务 id 与 md5 记录的账本；资料目录自身无台账。
- 既有安装用一次性 `install migrate` 迁移：运行状态进代码目录、原文与推送件留在资料目录、私有环境在代码目录重建。
- 代码目录新增运行时目录必须在 `.gitignore` 内，避免 `git status` 被运行状态污染；同时接受 `git clean -xdf` 会删除运行状态的风险。

### 3. 启动方式与权限

- 安装流程由宿主 agent 启动控制台（复用现有 detached + 新控制台窗口的机制）。
- 控制台启动时自检权限：若需要写飞书凭据库或写资料目录而当前权限不足，打印"请双击 `<code>/bin/frontier-console.cmd` 以完整权限重启"，保留进度并允许续接。
- 新开子终端**不能**换权限（子进程继承同一受限令牌），因此不把"另开终端"当作权限方案。
- 单实例锁、心跳（沿用现有字段与 60 秒重写）、滚动日志都放在代码目录的控制台状态区。

### 4. 飞书事件面与两层白名单

- 事件面同时消费 `im.message.receive_v1` 与 `card.action.trigger`；只接受已核实 owner 的单聊。
- **指令白名单**：自然语言或 `/` 指令，与实际文本 trim 后**精确匹配**；命中即直接执行对应操作，不做模糊匹配。
- 未命中时启动一次**意图判定运行**：只读、不取执行端租约、独立于推送单飞行锁，强制输出受 schema 约束的 JSON（操作 id + 参数 + 理由），操作 id 必须属于操作白名单；60–90 秒上限，同一时刻最多一个，同一文本 10 分钟内复用结果；失败回复"无法判断"。
- 判定命中 → 发送**确认卡片**（操作、参数、明确"不修改 frontier 程序本身"，`执行`/`取消` 两个按钮；10 分钟过期；一次性 nonce 保证重复点击幂等；仅 owner 点击有效）→ 用户点击后执行 → 回执。判定无对应操作 → 回复无权限。
- **卡片按钮（评分、采纳/拒绝）不走这套**：它们属于既有推送反馈流程，点击即按既有规则生效。
- 执行端只接受"操作 id + 校验过的参数"，绝不把用户原文透传给 agent 执行。
- owner 身份来源改为 `/frontier-init` 的传输测试：用测试消息的发送者与登录身份核对后写 `recipient.json`。**临时关键词 smoke 闭环退役**，其检索/评分/采纳验证并入 `/frontier-update-kb` 结尾的首次正式推送演练。

### 5. 操作白名单 v1

操作集合（写入仓库契约并机读）：`status`、`push_again`、`process_feedback`、`pause`、`resume`、`test_message`、`change_schedule`、`relocate_archive`。

明确排除：`init`、`update_kb`（需要终端逐条交互）、`stop_service`（与关闭窗口重复）、任何修改 frontier 代码、配置定义或权限范围的请求。排除项在飞书端只回复"请在控制台执行"。

### 6. 服务生命周期

- 每日一个推送时刻，默认 08:00（用户时区），可由 `change_schedule` 修改；v1 不支持多时段与工作日过滤。
- 补推：控制台启动或从暂停恢复时，若当天还没有推送请求，立即发起一次；错过多天仍只合并成一次待推请求。
- `/frontier-start` / `/frontier-stop` 启停服务；暂停 = 停止定时推送与飞书响应，控制台仍在前台并显示已暂停，期间只回复暂停提示、不派生任何运行。
- 重新打开控制台按上次状态恢复：上次为暂停则保持暂停，上次为运行态则自动启动服务。
- 知识库未就绪时服务照常运行，但每日推送被门禁挡住，控制台明示"待初始化知识库"；`/frontier-update-kb` 完成后自动放行。
- 关闭窗口时显式终止在飞的 agent 运行（不再依赖"下次检查停止哨兵"），把当前请求标为未完成，交由既有"恢复未完成工作"机制续接。

### 7. `/frontier-init`

在控制台内完成，按步骤续接（已完成步骤记录在代码目录的初始化状态里，重跑时跳过）：

1. 确认资料目录：`Y/y` 用默认；`N/n` 打开系统文件夹对话框选择，允许工作区外目录，但要求控制台无沙箱写入。
2. 确认执行 agent：v1 只有 DeepSeek Harness 适配器；展示可执行文件路径、凭据补丁与授权范围。
3. Lark CLI 三级检测：未安装 → 私有安装（代码目录）；未登录 → 设备码登录（`auth login --no-wait` → 浏览器授权 → `auth login --device-code`）；权限或 scope 不足 → 给出飞书开发者后台链接与缺失清单。所有步骤在控制台内完成，**不新开系统终端**；失败时给"重试 / 中止（进度保留）"，不允许跳过进入下一步；等待上限 15 分钟。
4. 发送测试 HTML 与单按钮测试卡片并等待点击；同时用消息发送者验证 owner 并写 `recipient.json`。
5. 设施命名：Base 名、原文云盘目录名、推送云盘目录名三项，回车用默认、输入覆盖；表名固定不暴露；已存在同名设施询问复用或新建。
6. 选择每日推送时刻。
7. 询问是否初始化知识库：是 → 进入 `/frontier-update-kb`；否 → 结束初始化，服务启动但推送被门禁挡住。

设施（Base、各表、两个云盘目录）由控制台自动创建，不再要求用户集中确认展示名称之外的命名。正式服务运行时拒绝重跑 `/frontier-init`。

### 8. `/frontier-update-kb`

1. 暂停正式服务（定时推送与飞书响应），记录恢复状态。
2. 用系统文件夹对话框选择目录；目录内的文件**复制**进资料目录 `originals/`（md5 校验，原目录不动），并按既有库流程上传云盘。
3. 控制台编排分片读取：一批文件的总量按上下文窗口约 10% 打包（以字符估算），**不做单文件分片**；单个文件可独立超预算；单文件估算超过窗口 50% 记为"未读取（超出读取上限）"并在结束报告列出；最多 2 个并发子运行，串行提交，单个失败重试一次后跳过。
4. 每个读取子运行只产出候选知识卡片与命题到候选区，不写知识库；由控制台合并去重后进入审阅。
5. 逐条打印审阅：**Enter 接受**、**Backspace 丢弃**、**Tab 保留但打 `Under review` 标签**；`q`/Esc 中止，已决定的立即生效，未决定的留待下次；每条显示 `第 N / M`；stdin 不是 TTY 时拒绝进入审阅。
6. 审阅决定写入代码目录的逐条决定记录；被丢弃的候选不写入知识库但保留在候选区与决定记录中；审阅结束仍写整批确认（含 hash 与决定摘要），写入时按决定处理。
7. 完成后恢复服务，并执行一次首次正式推送演练作为真实链路证据。
8. 重复执行是增量：只读取资料目录中尚未登记的文件。

### 9. `Under review` 的数据与生效

- 知识卡片与命题各新增一个**可选**布尔字段 `under_review`（缺省 false），Base 对应「待复核」勾选框列。
- 该字段**不设为必备字段**：缺失视为 false，既有 Base 在下次初始化或接入时补列，不升级不报错。
- `under_review` 的卡片与命题不参与检索计划、排序与写作上下文；仍同步 Base、仍参与比较、仍计入配额。语义是停用，不是删除。
- 用户在 Base 取消勾选后，经 `knowledge.cli pull` 回到本地权威。控制台每 10 分钟执行一次 `pull`，接管已退役的同步定时器；`pull` 接受该字段的编辑，但不写变更日志（保持变更日志只记 title / review / related_knowledge 的语义）。

### 10. Agent 运行

- 统一用 `dsh --profile headless --json` 启动 Agent 运行：控制台解析事件流、记录 `session_id` 到运行记录、只显示开始/结束/失败摘要，完整输出写入代码目录的日志。
- 必须复用安装记录里的 `--patch` 覆盖层（headless profile 出厂禁用账号凭据），否则运行会因缺少凭据失败。
- 沿用既有护栏：单飞行锁、执行端租约、安装报告存在阻塞项时拒绝、单次时限、失败不自动重试。
- 意图判定运行是独立的只读运行，不占执行端租约，不与推送运行共用单飞行锁。
- 现有注释记录 argv 约定已对 DSH 0.2.1-rc.3 验证，本机实际为 rc.5；实现时按实机版本复核任务作为最后一个位置参数的约定。

### 11. 迁移与兼容

- `install migrate`：把既有安装的运行状态、安装记录、执行端租约迁入代码目录运行时区；原文与推送件留在资料目录；私有环境在代码目录重建；私有 lark-cli 与安装记录一并迁移。
- 飞书 Base、云盘目录、知识库内容不因迁移而变化。
- 旧 `frontier-listener.cmd` 启停脚本在迁移时替换为控制台启停脚本。

## 验收标准

以下全部需要真实证据，缺一项只能记 `untested`，离线测试不能代替：

1. 控制台连续运行 ≥24 小时，事件流与日志无崩溃重启；
2. 至少一次每日推送由控制台计时真实到点触发，而不是手动发起；
3. 飞书指令白名单三条（`推一篇`/`处理反馈`/`状态`）真实往返；
4. 一条非白名单文本经意图判定产出确认卡片，点击后真实执行并回执；
5. 暂停与恢复各一次，暂停期间飞书只回暂停提示、不派生任何运行；
6. 关闭控制台窗口后服务确实停止（次日不推送、飞书无响应），重开后按上次状态恢复；
7. `/frontier-init` 全流程一次：含 Lark 安装/登录、测试 HTML 与带按钮卡片点击、三项命名、owner 身份写入；
8. `/frontier-update-kb` 全流程一次（小目录）：三种审阅决定都用到，`Under review` 卡片次日确实不参与检索；
9. 既有安装迁移一次，迁移后服务与知识库读写正常。

## 后果

- **代价**：服务可用性完全取决于用户是否打开了控制台；关窗口/重启机器后服务不在线。控制台需要一个交互层，而仓库此前没有任何 TTY/键盘读取代码，全部从零实现。控制台同时承担调度、事件面、agent 编排与审阅，代码面比监听进程更大，失败点更集中。
- **收益**：调度权、在线状态与运行信息归一到同一个用户可见的进程；"关窗口即停服务"语义明确；临时 smoke 闭环与两个宿主定时任务的验收负担消失；`Under review` 让初始化审阅可以先保留后决定。
- **安全边界**：飞书侧仍只接受 owner 单聊；指令白名单精确匹配；自由文本只能通过判定运行映射到封闭操作集合，且必须经确认卡片；执行只接受操作 id 与校验参数。ADR 0005 的单用户、单执行端约束继续有效。
- **证据语义变化**：`scheduled_run` 的"到点容差"证明与 `listener_health` 巡检都失去对象；定时是否真实到点改由控制台自己的运行记录证明。
- **不再被启动的旧路径**：`listener serve/start/stop/status/health`、`listener-check`、两个宿主定时任务、临时关键词 smoke 闭环。

## 实现状态

控制台、目录模型、`/frontier-init`、`/frontier-update-kb`、`Under review`、两层白名单与确认卡片均已实现并通过离线测试（spec #74 的 #75–#91）。旧监听进程、宿主定时任务与临时 smoke 闭环已退役。**真实验收项仍未取得全部证据**：逐项状态与证据位置见 [`docs/acceptance/README.md`](../acceptance/README.md)；在真实证据产生前，未执行项保持 `untested`，不得宣称控制台化已验收。

## 明确不做

多宿主适配（v1 只有 DSH）、多推送时段与工作日过滤、分栏 TUI、自由文本直接执行、为 Lark 新开系统终端、Windows 服务与登录自启、宿主定时任务、监听巡检、单文件分片读取。
