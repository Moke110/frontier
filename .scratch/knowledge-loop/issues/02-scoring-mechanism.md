## Question

我在微信里给出「推送质量评分」，这个信号**技术上怎么采、业界怎么采**？

需要查清两类事实：

**① Hermes 微信端的能力边界（本机实际情况）**
- 用户回复一条消息后，agent 能看到什么？回复是纯文本，还是带结构（引用的是哪条消息？可点按钮 / 快捷回复？）
- cron job 的 `attach_to_session` 如何把回复带回 agent？
- 一次推送若发多条消息，能否被**逐条**引用打分？
- 有无消息长度 / 格式限制影响评分回传？

**② 同类系统的反馈采集做法**
- RSS / LLM 简报类产品（Readwise、AlphaSignal、Papr、Inoreader AI、各类 newsletter）或研究型 digest 系统怎么让用户打分
- 采什么信号：显式评分 / 打开率 / 停留 / 收藏 / 忽略
- 怎么防止「用户嫌麻烦干脆不打分」

## Answer

**结论：微信通道上唯一可用的反馈 = 一条普通文本消息。** 没有按钮、没有快捷回复、没有 reaction；唯一被官方机制认可的结构化输入是 **「编号列表 + 回数字」**（`clarify` 工具的**文本回退**路径，因为 `weixin.py` **未实现 `send_clarify`**）。

### 已核实的平台能力边界

| 能力 | 微信（iLink） | 出处 |
|---|---|---|
| agent 收到**纯文本** | ✅ | `gateway/platforms/weixin.py:942-968` |
| 引用回复 → 内联为 `[引用: 标题 \| 正文]`，**无独立 id** | ✅（只有文本） | `weixin.py:946-961` |
| 原生按钮 | ❌ 未找到支持，**判定不可行** | 无 `send_clarify`（仅 `base.py` 空实现 + `whatsapp_cloud.py`） |
| 快捷回复 | ❌ 仅有「回复数字」**文本回退** | `tools/clarify_gateway.py:28-30`、`run.py:10200-10203` |
| 消息表情 / reaction | ❌ 事件不投递 | `weixin.py` grep 无 reaction 类型 |
| 单条出站上限 | **4000 字符**，超长按段落边界切块 | `weixin.md:252-259` |
| **实测旧日报正文长度** | **4152–5763 字符 → 一次投递被切成 2 条气泡，且气泡 ≠ 条目** | 8 份 `cron/output/*.txt` 实测 |
| 入站多条快发 | **3 秒防抖合并成一条**（`\n` 拼接） | `weixin.md:126`、`weixin.py:1510-1549` |
| 打开率 / 停留 / 已读 | ❌ iLink 不投递，**判定不可行** | `weixin.py` 无相关字段 |

### 手交给票 08 的建议（研究结论，非决定）

1. **主信号 = 「编号 + 单 token」，一条消息打完**：`1👍 2👎 3👍 4👎`。依据：唯一官方认可的结构化输入；且**旧日报正文本来就在邀请「回复序号（1–4）」追问**，用户已有肌肉记忆（`output/20261009` 正文实测）。
2. **不要靠引用气泡定位条目** —— 气泡 ≠ 条目，切分点在段落边界。
3. **显式评分要「少、可沉默、能被隐式信号补」**：只做**二元（👍/👎 或 `+`/`-`）+ 可选一句话**，允许整条不回（沉默 = 默认保留）。业界一致：多档强制打分回收率最低（AlphaSignal 只做一键 upvote；Readwise 干脆用「高亮/保存」代替打分；BPR/Hu 以隐式反馈为主）。
4. **隐式信号里「是否追问该条目」= 最强正信号**（零额外动作、会话里天然可得），代价是稀疏且有偏（「没反应」既可能是不感兴趣也可能是没看）。

### ⚠️ 关键：与票 10 的「表面冲突」及解法（本票最重要的产出）

票 02 的结论 2 说「**必须开 `attach_to_session=true`**，否则 agent 对简报失忆、编号无从对应」；票 10 证明**卡片流走的不是 cron 投递通道**（而是 `hermes send` 直发）→ 卡片刻**不进会话历史** → `attach_to_session` **对卡片流无效**。

这不是矛盾，是**同一个目标的两种实现，其中一种在卡片流下不可用**：

- 两票**一致**的部分：定位都靠**稳定编号**，都不靠引用（引用无 id）。
- 目标相同：agent 必须知道「编号 ↔ 卡片全文」的对应关系。
- 票 02 的**桥**（会话镜像）不可用 → **桥必须换成「当日推送的 manifest 文件」**（如 `runs/<date>.json` / `digests/<date>_cards.json`，卡片发出时同步落盘）。

**这个替换是净收益，不是妥协**：
1. 票 06 把 `attach_to_session` 归类为 **Hermes 专有** —— 用 manifest 文件则**换任何 agent 都成立**；
2. 它与票 06 推荐的「**状态机 + 状态文件**（`fetch → select → write → archive → update_kb → push`，每阶段写 `Status`）」是同一个东西，**一物两用**；
3. 它还顺带修掉了票 02 指出的另一处缺陷：mirror 进会话的是「整篇简报一个 turn」，而 manifest 可以做到**卡片级**粒度。

→ **结论：卡片流的上下文桥 = 当日 manifest 文件（不是会话镜像）。** 已写入票 08 的框架约束。
